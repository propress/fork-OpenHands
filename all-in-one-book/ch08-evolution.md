# 第八章：项目演进史——从 OpenDevin 到 OpenHands V1

> 了解一个系统的现在，最好的方式之一是理解它的过去。OpenHands 的架构不是一蹴而就的，它经历了从学术原型到工程产品、从单体到分层、从 V0 到 V1 的演进过程。这一章通过梳理项目的演变脉络，帮助你理解为什么系统现在是这个样子——那些看似奇怪的设计决策背后，往往有合理的历史原因。

> **注意**：本仓库是一个浅克隆（shallow clone），仅保留了最近几个提交。本章的演进史主要基于：代码库中的架构文档、遗留代码注释（LEGACY V0）、公开技术报告、README 和 CREDITS 文件中的历史信息，以及从代码结构推断的演进痕迹。

---

## 8.1 起点：学术研究项目 OpenDevin（2024 年初）

OpenHands 最初以 **OpenDevin** 为名出现，由学术界推动，目标是复现和超越当时最先进的 AI 软件工程代理（Devin by Cognition Labs）。

项目的理论基础来自几篇关键论文：
- **CodeAct（2024年2月）**：提出用代码统一所有 Agent 动作的设计范式
- **SWE-bench**：衡量 AI 解决真实 GitHub Issue 能力的基准测试

**早期架构的基本形态（第一阶段）：**

```
┌─────────────────────────────────────────┐
│            OpenDevin（早期）              │
│                                          │
│  ┌──────────┐    ┌─────────────────────┐ │
│  │  Agent   │───→│   EventStream       │ │
│  │(CodeAct) │    │  （Action/Obs 总线） │ │
│  └──────────┘    └──────────┬──────────┘ │
│                             │             │
│                    ┌────────▼────────┐    │
│                    │    Runtime      │    │
│                    │ (Docker 容器)   │    │
│                    └─────────────────┘    │
│                                          │
│     简单的命令行界面 + 基础 Web UI        │
└─────────────────────────────────────────┘
```

这个阶段的核心机制——EventStream、Action/Observation、CodeAct 范式——已经成形。这些后来成为整个系统最持久的设计遗产。

## 8.2 快速成长：功能扩展阶段（2024 年中）

项目更名为 **OpenHands**，从学术原型演进为功能完整的开源产品。这个阶段的特征是：快速添加功能，架构逐渐复杂。

**主要新增能力：**

1. **多 Agent 系统**：引入 `AgentDelegateAction`，支持主 Agent 把子任务委派给专门的子 Agent。`BrowsingAgent` 等专家 Agent 出现。

2. **浏览器集成**：通过 Playwright 实现真正的浏览器操控，Agent 可以与网页交互。

3. **Microagent 系统**：从硬编码的提示工程发展为可扩展的知识注入机制。

4. **记忆系统演进**：从"简单截断"发展为 Condenser 体系，支持多种策略。

5. **VS Code 插件**：Agent 的工作环境从纯命令行扩展到集成开发环境。

**这个阶段的架构（第二阶段）：**

```
┌───────────────────────────────────────────────────────┐
│                    OpenHands V0                        │
│                                                        │
│  Web UI  ←→  WebSocket  ←→  openhands/server/         │
│                                  │                     │
│                         AgentController               │
│                         ┌────────┤                    │
│                         │        │                    │
│                  ┌──────▼──┐  ┌──▼──────────────┐    │
│                  │CodeAct  │  │  EventStream     │    │
│                  │Agent    │  │  （持久化+广播）  │    │
│                  └─────────┘  └──────┬───────────┘    │
│                                      │                 │
│              ┌───────────────────────┤                 │
│              │                       │                 │
│        ┌─────▼──────┐  ┌────────────▼────────────┐   │
│        │ DockerRuntime│  │  Memory/Condenser       │   │
│        │ （沙箱管理） │  │  Microagent 系统         │   │
│        └─────────────┘  └─────────────────────────┘   │
│                                                        │
│        212 个文件标注 LEGACY V0 的代码都在这个阶段形成  │
└───────────────────────────────────────────────────────┘
```

这个阶段的架构称为 **V0**，它功能完整，但所有代码都在同一个仓库，边界不够清晰。

## 8.3 遇到的问题：单体架构的局限

随着功能增加，V0 架构暴露出几个问题：

**问题一：代码库过于庞大**
Agent 核心逻辑、服务器代码、前端代码、运行时代码全部混合在一个仓库中，维护和贡献变得困难。

**问题二：扩展性瓶颈**
V0 的 AgentController 和 Runtime 是紧耦合的——Runtime 必须在和主进程同一台机器上运行，无法轻松扩展到云端。

**问题三：SDK 需求**
用户希望能通过编程 API 使用 OpenHands 的代理能力，而不只是通过 Web UI。V0 的架构没有为此设计干净的边界。

**问题四：企业级功能与开源核心的分离**
Slack 集成、多用户管理、权限系统等企业功能需要一个清晰的分层来避免污染开源核心。

---

## 8.4 架构重塑：V0 到 V1 的迁移（2025 年）

为了解决上述问题，团队启动了一次重大架构重塑，核心思路是：**把 Agent 核心逻辑从应用服务器中剥离出去**。

**迁移的两条主线：**

**主线一：Agent 核心 → Software Agent SDK**

Agent 的决策逻辑、工具调用、记忆管理等"大脑"部分，被抽离到一个独立的 Python 库（Software Agent SDK），托管在单独的仓库。

这样，任何 Python 应用都可以通过 `pip install` 使用 OpenHands 的代理能力，而不需要运行整个 Web 服务。

**主线二：应用服务器 → openhands/app_server/**

在本仓库中，新建了 `openhands/app_server/`，这是一个干净的 FastAPI 应用服务器，负责：
- 对话生命周期管理（创建、暂停、恢复）
- 沙箱管理（通过 Sandbox API）
- 用户认证和授权
- 事件的 HTTP/WebSocket 路由
- 与 Software Agent SDK 的集成

**V1 架构（第三阶段）：**

```
┌─────────────────────────────────────────────────────────────┐
│                    本仓库（OpenHands）                        │
│                                                              │
│  前端（React）         openhands/app_server/（FastAPI）       │
│       ↕ HTTP/WS       ┌──────────────────────────────────┐  │
│                       │ /app_conversation → 对话管理      │  │
│                       │ /sandbox         → 沙箱管理       │  │
│                       │ /event           → 事件 API       │  │
│                       │ /user            → 用户管理       │  │
│                       └──────────────────┬───────────────┘  │
│                                          │ SDK 调用          │
└──────────────────────────────────────────┼──────────────────┘
                                           │
┌──────────────────────────────────────────▼──────────────────┐
│               Software Agent SDK（外部仓库）                  │
│                                                              │
│  ┌───────────────┐  ┌───────────────┐  ┌─────────────────┐  │
│  │  Agent 核心   │  │  LLM 封装     │  │  记忆/Condenser │  │
│  │  决策循环     │  │  Function Call│  │  上下文管理     │  │
│  └───────────────┘  └───────────────┘  └─────────────────┘  │
└─────────────────────────────────────────────────────────────┘
```

## 8.5 遗留代码：212 个文件的"化石层"

目前本仓库中有 212 个 Python 文件带有这样的注释：

```python
# IMPORTANT: LEGACY V0 CODE - Deprecated since version 1.0.0,
# scheduled for removal April 1, 2026
```

这些文件构成了完整的 V0 实现——包括我们前面几章深入分析的 AgentController、CodeActAgent、DockerRuntime 等。

为什么还没删除？**向后兼容和渐进迁移。** 虽然 V1 是未来方向，但许多生产环境、集成测试、现有用户都依赖 V0 的代码路径。迁移是渐进的，而不是一刀切的。

从开发者的角度，这 212 个文件是最完整、最易读的 OpenHands 核心机制参考——这也正是为什么本书前几章主要基于 V0 代码来讲解原理。V0 和 V1 的设计思想一致，V1 只是边界更清晰。

## 8.6 CodeActAgent 的自身演进

除了系统架构的演进，核心 Agent 自身也经历了多次迭代。CodeActAgent 现在的版本是 **2.2**，这个版本号反映了它的能力积累：

**版本演进的主要节点（从代码痕迹推断）：**

- **1.x 阶段**：基础的 CodeAct 实现，bash + Python 工具
- **2.0 阶段**：引入 `str_replace_editor`（来自 openhands-aci 库），提升文件编辑的精确性，取代之前的 LLM-based 编辑方式
- **2.1 阶段**：改进 Condenser 集成，使记忆管理更可靠
- **2.2 阶段（当前）**：引入 `task_tracker` 工具（Plan 模式），Agent 可以维护结构化任务清单，处理复杂多步任务

`str_replace_editor` 的引入特别值得一提。它来自 `openhands-aci` 库（OpenHands ACI = Agent-Computer Interface），提供了类似文本编辑器的精确行级编辑接口，避免了"让 LLM 重写整个文件"这种容易出错的方式。

## 8.7 企业功能的演进：`enterprise/` 目录

本仓库的 `enterprise/` 目录包含了"源码可见但需授权使用"的企业功能：

```
enterprise/
├── 用户认证（Keycloak 集成）
├── 数据库迁移（Alembic）
├── 第三方集成（GitHub、GitLab、Jira、Linear、Slack）
├── 计费系统（Stripe 集成）
└── 遥测和分析（PostHog、自定义指标）
```

这个目录的存在，说明了一个开源商业项目的典型架构策略：**开源核心 + 源码可见的商业扩展**（不同于完全闭源），这让企业客户可以评估和审计代码，同时通过许可证保护商业利益。

---

## 8.8 演进的规律：三个持久的设计原则

回顾整个演进历史，有三个设计原则贯穿始终，无论架构如何变化都未曾改变：

**原则一：EventStream 是系统的中枢**
从最早的 OpenDevin 原型到今天的 V1，EventStream 作为"所有通信走事件总线"的设计从未动摇。这是因为它带来的可调试性、可回放性、解耦能力是长期价值的。

**原则二：代码优先（CodeAct）**
用代码表达一切动作，用真实的执行结果作为反馈——这个范式从最初的论文启发到今天仍然是核心。没有任何迹象显示会转向"自然语言规划"模式。

**原则三：沙箱隔离**
无论是 Docker、Kubernetes 还是云端远程沙箱，都坚持"Agent 执行代码必须在隔离环境中"这一原则。安全性是不可妥协的。

---

从演进史的角度，OpenHands 展示了一个健康的开源项目应有的特征：从解决具体问题出发，快速积累功能，然后在积累了足够多的使用经验后，有勇气做架构重塑，而不是一直在既有架构上打补丁。
